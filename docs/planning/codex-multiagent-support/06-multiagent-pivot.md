## Clean Architecture: слои и где именно проходит граница repo

Направление зависимостей — только внутрь (Dependency Rule). Раскладка по кольцам, не абстрактно, а с точным указанием, что в каком репозитории:

| Кольцо | Содержимое | Репозиторий |
|---|---|---|
| **Entities** (домен) | `Event{Status, Message, SessionID, CWD, ToolName, ToolInput}`, `Status` enum | `notification_plugin_go` — это ядро ПРОДУКТА уведомлений, не generic plugin-инфраструктура, ей не место в SDK |
| **Use Cases** (бизнес-правила) | `ClassifyMessage`, dedup-политика, config-резолв (какой звук/тайтл на какой статус), webhook-форматирование | `notification_plugin_go` — та же причина |
| **Interface Adapters — decode** | Типизированный decode payload→`Event` для каждого агента (Codex/Claude/Cursor/OpenCode/...) | **`plugin-kit-ai`** (SDK) — это ровно generic "как получить типизированное событие от N хостов", то, для чего SDK и существует |
| **Interface Adapters — presenters** | `notifier` (desktop/webhook доставка), session-naming, click-to-focus | `notification_plugin_go` |
| **Frameworks & Drivers** | CLI-подкоманды (`handle-hook`, `handle-codex-hook`), OS API (macOS AX/Windows toast/Linux dbus), инсталлятор/marketplace-регистрация | `notification_plugin_go` |

**Граница repo проходит РОВНО по границе кольца "decode".** Всё, что "как понять, кто зовёт, и разобрать его JSON в типизированную структуру" — generic, идёт в plugin-kit-ai. Всё, что "что этот факт значит для уведомления человеку" — product-specific бизнes-логика, остаётся в notification_plugin_go.

## SOLID — конкретно, не декларативно

- **SRP**: три пакета — три разные причины для изменения. `plugin-kit-ai`'s host-detection меняется, когда у агента меняется формат payload/добавляется новый агент. `notification_plugin_go`'s classify/notify меняется, когда меняется бизнес-логика уведомлений (новая эвристика, новый звук). Installer меняется, когда меняется способ доставки бинаря/регистрации хуков. Три разных "кто это чинит", три разных релизных цикла.
- **OCP**: добавление агента = новый пакет в `plugin-kit-ai` (по образцу уже готового `internal/product`-паттерна bolzzzz — приоритетная цепочка `Detect()`, легко расширяемая новым `case`), БЕЗ модификации существующих Codex/Claude-декодеров. `notification_plugin_go` не меняется вообще при добавлении нового агента, если его событие укладывается в существующий `Event`-контракт.
- **LSP**: все per-agent decoder'ы обязаны быть взаимозаменяемы — `notification_plugin_go`'s код, потребляющий `Event`, не должен знать/заботиться, откуда он (Codex/Claude/Cursor). Если декодер конкретного агента нарушает это (например, поле означает что-то другое при том же имени) — это LSP-нарушение, ловить на ревью.
- **ISP**: installer НЕ единый "толстый" интерфейс на все агенты. Каждый agent-connector реализует только то, что ему нужно — Codex-connector не обязан знать про TOML surgical insert (это нужно только Cursor/legacy-notify-агентам), Cursor-connector не обязан знать про marketplace-trust-key-семантику.
- **DIP**: `notification_plugin_go`'s `Handler`/`Notifier` зависит от абстракции `EventSource` (интерфейс, отдающий `Event`), не от конкретных Codex/Claude/Cursor-пакетов напрямую. Конкретные реализации инъектируются на уровне `cmd/` (composition root — `main.go`), не хардкодятся вглубь бизнес-логики. Ровно то же самое, что уже делает сам plugin-kit-ai SDK внутри себя (`runtime.Descriptor`/`Engine.Dispatch` не знает про конкретные Codex/Claude типы — только про интерфейс Decode/Encode).

## Инсталлятор: не выброшен, слоистый, плюс мониторинг (по прямому требованию пользователя)

Единый бинарь остаётся точкой входа для юзера — конфиг, доставка (звуки/click-to-focus/dedup/webhook), и, что не было в исходном плане, **мониторинг**: новая подкоманда `agent-notifications status` (или `doctor`) — показывает по каждому подключённому агенту: обнаружен ли (бинарь агента в PATH/версия), хуки зарегистрированы ли, доверие есть ли (где применимо), бинарь актуален ли. Ни одна нативная per-agent-система (Codex marketplace, Cursor hooks.json) этого дать не может — каждая знает только про себя.

Внутри — два режима per-agent connector'а, выбираемые автоматически по тому, что поддерживает конкретный агент (эмпирически подтверждено сегодня, не предположение):
1. **Marketplace-based** (Codex подтверждён; Claude — наш уже существующий путь; CodeBuddy — вероятно, не проверено): регистрация через нативный `<agent> plugin add`-аналог. Существенно упрощено находкой сегодняшнего дня — trust-ключ для Codex keyed по `plugin_id:relative_path`, НЕ по command-строке (подтверждено чтением исходника `openai/codex`, юнит-тестом) → **не нужен** ни content-hash TOCTOU-guard, ни "frozen argv навсегда" (можно свободно менять путь к бинарю/wrapper-логику между релизами, пока не меняется plugin_id и относительный путь к hooks-файлу). `PLUGIN_ROOT` резолвится агентом нативно для plugin-bundled хуков — не нужен и pointer-file-костыль из старой §2.8.
2. **Manual-merge-based** (Cursor подтверждён — у него нет marketplace для хуков вообще, только сырой `~/.cursor/hooks.json`, что подтверждено README форка bolzzzz, который поэтому написал ИМ отдельную подкоманду `install-cursor-hooks`; OpenCode — не проверено, вероятно тоже нет marketplace): используется старая, уже тщательно спроектированная (owner-marker, flock, atomic write, backup, content-hash guard) машинерия из исходной Фазы 2 — она **не выбрасывается**, а становится вторым режимом, применяемым именно к агентам без родного marketplace.

Один-единственный manual-trust-шаг (`/hooks`-аналог) там, где он есть — не автоматизируется ни в каком режиме, это фундаментальное свойство самого агента, не наше архитектурное решение.

## Открытые вопросы, требующие проверки ПЕРЕД реализацией (по прямому указанию пользователя — не спешить)

1. ~~**OpenCode**: есть ли у него нативная marketplace-система для хуков...~~ **ЗАКРЫТО (2026-09-01, deep-dive агент прочитал исходники форка bolzzzz напрямую).** Нет marketplace вообще — единственный интеграционный файл `.opencode/plugins/notifications.ts`, TS-шим, форвардящий события в Go-бинарь через `spawn(bin, ["handle-hook", event, "--product", "opencode"])` по stdin. `install.sh` не содержит ни одного упоминания opencode — только скачивает бинарь. Бинарь резолвится по цепочке: `$AGENT_NOTIFICATIONS_BIN` → `$CLAUDE_PLUGIN_ROOT/bin/...` → `<файл-плагина>/../../bin/` (чекаут репо) → PATH. **Вывод: OpenCode однозначно попадает в manual-merge-режим (режим 2)**, ручное размещение файла + указание на бинарь, ничего автоматического. Осталась только неподтверждённая деталь: реальный ли у opencode discovery-каталог `.opencode/plugins/` (мн.ч., как у форка) или `.opencode/plugin/` (ед.ч.) — сверить с документацией opencode перед реализацией.
2. ~~**Cursor**: подтверждено косвенно (README форка)...~~ **ЗАКРЫТО эмпирически через прямое чтение исходника** (`cmd/agent-notifications/cursor_hooks.go`, не только README). Подтверждено: никакого marketplace, только сырой `~/.cursor/hooks.json`. Их реализация (`install-cursor-hooks`/`uninstall-cursor-hooks`) — хороший референс для нашей manual-merge машинерии: atomic write (temp+rename, chmod сохраняет права), сохранение неизвестных top-level и non-agent hook-полей (парсинг в `map[string]json.RawMessage`), idempotent strip-then-add (перезапуск не дублирует). НО у них слабее, чем то, что мы уже спроектировали в исходной Фазе 2: owner-marker — это substring-match по command (`Contains("handle-hook") && Contains("--product cursor")`), не выделенное поле — хрупко (может случайно задеть чужой хук с тем же текстом); нет flock; нет backup-файла. **Решение: сохраняем нашу более тщательную версию (настоящий owner-marker, flock, backup) поверх их доказанно рабочего atomic-write/idempotent скелета.** Отдельно найден cautionary-паттерн — `cursor_approval.go`: у Cursor нет события "жду approval", их gate стреляет ДО того как Cursor решил нужно ли разрешение; воркэраунд — detached watcher-процесс с grace-period (8с по умолчанию), проверка "разрешено ли" через `/proc`(Linux)/`ps`(macOS), **недоступно на Windows** (там только grace-period). Держать в уме как пример хрупкого timing-based решения, если нам самим понадобится "угадывать" отсутствующее событие у какого-то агента.
3. **CodeBuddy**: заявлено hook-compatible с Claude Code — вероятно, тоже marketplace-based, но **всё ещё НЕ проверено** (deep-dive агент подтвердил только изоляцию конфига `~/.codebuddy/...` и env-детекцию `CODEBUDDY_*`, не сам install-механизм).
4. ~~Точный пакетный путь/имя нового host-detection-пакета...~~ **ЗАКРЫТО (2026-09-01).** Прочитана реальная структура SDK (`internal/runtime/engine.go`, `types.go`, `platformmeta/*`). Ключевая находка: `Engine.Dispatch` держит ОДИН `Resolver` на весь `App` (SDK рассчитан на "один плагин — одна нативная схема вызова для одного хоста", не на авто-детект среди N хостов под общим argv-контрактом) — у SDK сейчас нет готового паттерна для нашего сценария. `platformmeta` тоже не подходит — это чисто статические метаданные для доков/скаффолдинга (`NativeRoot: "~/.codex/plugins/..."` как строка для документации, не машиночитаемый env-маркер), без рантайм-сигналов.
   Пользователю предложены 3 варианта (с оценками надёжность/уверенность): (A, рекомендовано мной 8/8) держать как `internal/product` в самом `notification_plugin_go`, по образцу bolzzzz — SDK не имеет такого паттерна ни у одного другого потребителя; (B, 6/7) новый публичный пакет `sdk/hostdetect`, пир к `sdk/codex`/`sdk/claude`/`sdk/platformmeta`; (C, 4/5) встроить в сам `Engine`/`Resolver` (composable resolver) — большой риск регресса, трогает всех потребителей SDK.
   **Пользователь выбрал (B) — `sdk/hostdetect`.**
   Дизайн пакета:
   - Файлы: `hostdetect_claude.go` / `hostdetect_codex.go` / `hostdetect_cursor.go` / `hostdetect_codebuddy.go` / `hostdetect_opencode.go` (каждый — свой `Signal`, расширение = новый файл, не правка существующих), `signals.go` (приоритетный `DefaultRegistry []Signal`, порядок как у bolzzzz: CodeBuddy → Cursor → Codex → Claude по умолчанию, OpenCode — явное поле в payload, приоритет выше всех), `detect.go`, `doc.go`.
   - API: `type Platform string` (значения `"claude"/"codex"/"cursor"/"codebuddy"/"opencode"` — совпадают с текущим значением флага `--product` в `notification_plugin_go`, drop-in); `type Env interface { LookupEnv(string) (string, bool) }`; `type Signal struct { Platform Platform; EnvMarkers []string; PayloadSniff func(raw map[string]any) bool }`; `var DefaultRegistry []Signal`; `func Detect(override string, env Env, payload []byte) Platform`.
   - `PayloadSniff` — лёгкий, смотрит только верхнеуровневые JSON-ключи (`turn_id`, явный `"product"` и т.п.), НЕ типизированный decode — чтобы не тянуть зависимость на `sdk/codex`/`sdk/claude` и не создать цикл импортов.
   - `DefaultRegistry` — `var`, не хардкод внутри `Detect()` — сторонний потребитель может `append` свою платформу без форка пакета (OCP).
   Реализация пакета ЕЩЁ НЕ НАЧАТА — только дизайн зафиксирован, ждём подтверждения пользователя на старт кодирования.
5. **(Новое, подтверждено, не требует проверки — просто фиксация факта)** Команды `status`/`doctor`/мониторинга в форке bolzzzz **не существует вообще** — полный список команд их `main.go`: `handle-hook`, `focus-window(s)`, `play-sound`, `cursor-approval-watch`, `daemon`, `windows-hooks`, `install-cursor-hooks`, `uninstall-cursor-hooks`, `version`, `help`. Значит наша идея такой команды (см. раздел «Инсталлятор» выше) — это полностью самостоятельная разработка, референса скопировать неоткуда, весь дизайн (что показывать, откуда брать статус per-agent) — наш.
