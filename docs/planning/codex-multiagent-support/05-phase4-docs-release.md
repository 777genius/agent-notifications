## РЕВИЗИЯ после 3 критиков фазы 4

### 4.1/4.4/4.6 — позиционирование переписано (критик: "beta" без прецедента и слишком расплывчато)

**Факт**: в этом репо НЕТ прецедента "beta"/"experimental"-лейбла вообще (grep = 0). Вводить его — новая, непонятная юзеру конвенция. Плюс: Windows-ситуация — это функциональный пробел (PermissionRequest физически недоставим на legacy-фолбэке, сама поддержка hooks не подтверждена), не "шероховатости" — заслуживает явной формулировки, а не общего hedge.

**Новый подход — platform/mechanism-specific формулировки вместо одного лейбла**:
- README: "Codex CLI support (new in vX.Y)" + секция **"Known Limitations"**: Windows — "не протестировано; поддержка hooks в Codex на Windows не подтверждена, при отсутствии — фолбэк на legacy notify, который не может доставлять permission-уведомления."
- **Новая секция README "Troubleshooting → Not getting Codex notifications?"** (критик дал точный список пунктов, включая САМЫЙ коварный — не входивший в исходные 7 research-items — неподтверждённое "фаерит ли `codex exec` вообще hooks-события"): (1) выполнен ли `/hooks` trust; (2) permission-уведомления приходят только когда Codex РЕАЛЬНО спрашивает разрешение, не в auto/bypass режимах; (3) нужна интерактивная сессия. **Критичное условие формулировки**: пункты 2 и "не-интерактивный `codex exec` не фаерит hooks" — сами НЕ подтверждены, формулировать как "ожидаемое поведение, требует подтверждения", не как факт.
- **4.6 — историческая рекомендация**: в release notes нельзя заявлять проверенную платформу заранее. Формулировка строится только из exact-head evidence; неподтверждённые платформы перечисляются в Known Limitations.
- Мелкие правки атрибуции: формат CHANGELOG — установленная конвенция ВСЕГО репозитория (Keep a Changelog+SemVer), не "формат из этого чата"; "11 lifecycle-событий Codex, 2 покрыты" — внешний, неподтверждённый счёт, смягчить формулировку ("остальные события Codex, вне scope v1") вместо жёсткого числа в публичном README.

### 4.3 — релизный гейт: список сценариев исправлен + гейт стал условным (критик нашёл, что план сам себе противоречил)

**Критичная находка**: список сценариев гейта ({№2,4,5,10}) противоречил собственной таксономии Фазы 3 — №4/№5 на деле класс C, не D; №5 **прямо противоречит** решению Фазы 3 убрать его из live (флейки, уже покрыт unit-тестом); и, главное, **гейт полностью пропускал №3 — само ядро фичи** (реально ли уведомление появляется на живом Stop, звук, click-to-focus). Как было написано, релиз мог пройти гейт, ни разу не подтвердив, что уведомление вообще приходит.

**Исправленный список гейта**: `{№2, №3, №10}` (принципиально ручные GUI/TUI-сценарии) + класс B `№7` (env-gated, автоматизируемо). №4 — по возможности, необязателен. №5 — исключён окончательно (уже в unit-тестах §3.3).

**Гейт — условный, не безусловный** (критик: проверил последние 4 реальных релиза этого репо — ни один не был про Codex; требовать живой Codex e2e перед КАЖДЫМ релизом ради несвязанного фикса — гарантированная десенсибилизация галочки именно к моменту, когда она важна): условие — механически детектируемое, `git diff vLAST..HEAD --name-only` пересекает `internal/codexhook/`, `handle-codex-*`, инсталлятор-пути. Если пересекает — гейт обязателен; если нет — пропускается явно, не молча.

**Место фиксации исправлено** (критик: "release-PR" в реальном флоу этого репо НЕ существует — шаг 4 `docs/RELEASE.md` это прямой `git commit`+`push`, без PR): фиксировать в теле release-коммита (trailer) или строке CHANGELOG-записи, не в несуществующем release-PR.

**Опциональный, не обязательный harder-механизм**: довесить в уже существующий CI-job `verify-version` (единственный реальный automated checkpoint в `release.yml`) детекцию тех же путей — если Codex-пути менялись и в коммит-трейлере нет маркера `Codex-e2e: <note>`, job падает с понятным сообщением. Честная оговорка (сам критик подчеркнул): CI не может проверить, что живой прогон РЕАЛЬНО был (нет логина/секретов/платного вызова на раннере) — это speed-bump/напоминание, не доказательство сути. Для solo-репо (подтверждено по авторам коммитов) — пропорционально; не городить GitHub Environment+required-reviewers (over-engineering, ревьюеров в репо нет).

**Точка вставки vs точка enforcement** — синхронизированы: чекбокс явно привязан к шагу 5 (`git tag`), не только "между 3 и 4".

### 4.5 — полностью переписан: 3 инварианта → 45, разделённые по механизму защиты (DOC vs CODE)

**Критик прочитал все 4 документа фаз полностью и нашёл ~45 инвариантов** против исходных 3 в этом разделе. Ключевая структурная поправка, определяющая весь раздел: **doc-заметка защищает АРХИТЕКТУРНОЕ решение ("не заводить второй config-путь"), но НЕ защищает конкретную строку кода, которую будущий рефакторинг случайно заденет** ("никто не читает CONTRIBUTING.md перед тем как слить два похожих на вид хендлера"). Поэтому: DOC-инварианты → новая секция в `docs/ARCHITECTURE.md` (существующий файл, 431 строка — правильный дом для "архитектурного why", подтверждено критиком; НЕ изобретать аналог CONTRIBUTING.md, он уже есть) + одна строка-указатель в `CLAUDE.md` в стиле уже существующего sh-prefix-предупреждения (`CLAUDE.md:7`, подтверждено дословно). CODE-инварианты → инлайн-комментарий ПРЯМО В ТОЙ ЖЕ строке/функции, добавленный **в том же PR**, что пишет эту строку — не отложенная документация.

**Уточнение прецедента**: `AGENT_CRITICAL_GUARDRAILS.md`, на который ссылается родительский workspace `CLAUDE.md`, **физически отсутствует** по указанному пути в этом чекауте (проверено критиком) — ссылка из workspace-заметок сейчас висит в пустоте для этого конкретно репо; не полагаться на него как на формат-прецедент здесь.

**Полный список по тирам (severity-first, из отчёта критика; для каждого — источник и механизм защиты)**:

**Tier 1 — ломает trust-хэш** (молча: у ВСЕХ существующих юзеров хуки перестают фаериться до ручного ре-trust): (1) frozen argv-строка целиком [BOTH]; (2) путь бинаря в hooks.json обязан быть стабильным/неверсионированным — отдельная от (1) половина контракта, ранее не выделена явно [BOTH]; (3) имена событий без префикса "Codex" — намеренно иначе, чем в SDK [DOC]; (4) `handleCodexHook` читает только `os.Args[2]`, никогда `flag.Parse()` — иначе `--owner=` может быть случайно съеден "чисткой" аргументов [CODE, обязателен инлайн].

**Tier 2 — молчаливая потеря данных/порча** (файлы юзера, чужие конфиги, без отката): (5) content-hash guard, не mtime+size [BOTH]; (6) backup — точные байты hash-снимка, не свежее перечтение [CODE]; (7) verify-then-delete-backup порядок, backup остаётся по умолчанию [BOTH]; (8) owner-поиск — токен-подстрока, не exact-match [BOTH]; (9) canonical-reset ВСЕГДА, но раздельно frozen command-string vs resettable metadata [BOTH]; (10) TOML — только хирургическая вставка, никогда decode+reencode [CODE]; (11) TOML footgun с `[table]`-секциями [CODE + тест уже в §3.4]; (12) **`state.go:176` намеренно БЕЗ default для `permission_request` — обратный инвариант**, кто-то "доделывающий" switch добавит ветку и permission-уведомления начнут молча попадать под question-cooldown [CODE, обязателен инлайн]; (13) legacy-uninstall тоже убирает `notify` из `config.toml` [BOTH].
